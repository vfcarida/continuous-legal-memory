# Continuous Legal Memory — Architecture & Engineering Roadmap

## 1. Vision & Architectural North Star

**Continuous Legal Memory (CLM)** is an open-source, bi-temporal cognitive memory and normative compliance framework engineered for legal AI agents and regulated enterprise systems.

While general-purpose agent memory frameworks (`mem0`, `letta`, `graphiti`) treat stored facts as flat semantic chunks, legal and regulatory reasoning is governed by formal jurisprudence:
1. **Tri-Canon Normative Hierarchy:** Higher-authority statutes override subordinate policies (*lex superior derogat legi inferiori*), specific provisions override general clauses (*lex specialis derogat legi generali*), and later provisions override earlier provisions *in pari materia* (*lex posterior derogat legi priori*), alongside explicit `SUPERSEDES` graph edges.
2. **Bi-Temporal Validity:** Every legal norm tracks both **valid time** (`valid_from` / `valid_to`, when a rule is legally in force) and **transaction time** (`transaction_time`, when the system recorded the rule), enabling reproducible point-in-time compliance audits.
3. **Epistemic Abstention & Oversight (EU AI Act Art. 14):** When query-to-memory alignment falls below a calibrated epistemic threshold (`min_similarity_threshold`) or Split-Conformal calibration ($1 - \alpha$) yields an empty/ambiguous set, the orchestrator explicitly abstains (`abstained=True`) rather than extrapolating unsupported legal conclusions.
4. **Verifiable Right-to-Erasure (GDPR Art. 17) & Post-Quantum Cryptographic Provenance (EU AI Act Art. 12):** Personal data is strictly confined away from neural parameters, erased across all four cognitive tiers (`Working`, `Episodic`, `Semantic Graph`, `Retrieval Buffer`) with 256-bit Sparse Merkle Tree non-membership proofs, and attested via **PQ-Hybrid-Ed25519-SHA256** (`Ed25519` + 67-chain `WOTS+-SHA256`), **RFC 8032 Ed25519**, or **HMAC-SHA256**.

## 2. Maturity Model & Quality Gates

Every subsystem in Continuous Legal Memory is governed by an explicit, test-verified maturity taxonomy. A component may only graduate to a higher tier when all corresponding engineering verification gates pass in CI:

| Maturity Tier | Engineering Criteria & Verification Gate |
| :--- | :--- |
| **`Stable`** | Complete implementation, strict static typing (`mypy` zero errors), clean linter status (`ruff` zero errors), deterministic unit & integration test coverage, and zero known drift between code and public documentation. |
| **`Beta`** | Functional implementation with unit test coverage and documented APIs; undergoing extended benchmark stress-testing or ecosystem integration validation. |
| **`Alpha` / `Experimental`** | Research or ablation module (such as online parametric weight adaptation in `ContinuousMemoryResearchHead`) isolated from default production paths and guarded by explicit runtime warnings. |
| **`Planned`** | Architectural design specified on the long-term research horizon; not yet shipped in the main package. |
